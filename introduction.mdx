SCALF is a scripting language built for predictability. Where other scripting ecosystems demand package managers, lockfiles managed by convention, and runtime surprises, SCALF takes a different path: static types catch mistakes before execution, a built-in permission sandbox blocks unexpected filesystem or network access, and every tool you need — formatter, type checker, test runner, standalone binary builder — ships inside the single `scalf` binary. There is nothing to install beyond the runtime itself. SCALF is implemented in Rust and designed to start fast, stay lean, and behave the same way every time.

## How SCALF Was Built

SCALF was developed incrementally across eight phases, each adding a cohesive layer of capability.

**Phase 1** established the language foundations: a lexer for all core token types, a recursive-descent parser covering expressions and statements, control-flow constructs (`if/else`, `while`, `for...in`, C-style `for`), function definitions and returns, and a working REPL that runs the full lex → parse → typecheck → evaluate loop.

**Phase 2** introduced the full type model: nullable types, unions, generics, and function types. Type annotation syntax was added to the parser, and an assignability-checking type inference pass was wired into both the REPL and CLI. Phase 2 also added several important syntax features: `def`/`return`, `value or default`, `or return err`, optional chaining with `?.`, postfix panic-unwrap with `!`, `match` expressions, and destructuring patterns.

**Phase 3** delivered the runtime interpreter: full execution of statements, expressions, functions, and module calls. List comprehensions, `use` imports for standard library modules, string methods (`trim`, `split`, `replace`, `uppercase`, `lowercase`), list methods (`push`, `pop`, `map`, `filter`, `reduce`, `sort`, `sorted`), and map methods (`get`, `set`, `has`, `keys`, `values`) were all implemented. Eight built-in standard library modules were added: `math`, `fs`, `json`, `path`, `env`, `http`, `time`, and `crypto`.

**Phase 4** introduced the permission model. The CLI flags `--allow-read`, `--allow-write`, `--allow-net`, `--allow-env`, `--allow-all`, and `--prompt-permissions` were implemented, and the runtime enforces them at every filesystem, network, and environment access point. The `http` module was also completed, supporting `get`, `post`, `put`, and `delete` with optional headers and timeouts. HTTP requests start immediately and resolve lazily so independent requests can overlap.

**Phase 5** added URL imports with content-addressed caching (SHA-256), lockfile generation and verification, and version pinning via the `@version` suffix. Namespace isolation ensures URL-imported modules cannot accidentally shadow local bindings.

**Phase 6** improved the developer experience with richer diagnostics: error codes, doc links, stack traces, concrete values in failure messages, and `did you mean …` suggestions for common lookup mistakes. The `scalf fmt`, `scalf check`, and `scalf test` subcommands were also introduced in this phase.

**Phase 7** delivered the bytecode VM and the standalone build system. The VM uses a stack-based instruction set with constant folding and is accessible via `scalf --vm`. `scalf build` embeds a script's source into a native binary, auto-selects Cargo features, and supports cross-compilation via target aliases or raw triples. A startup benchmark command measures cold-start performance against a time budget.

**Phase 8** added concurrency helpers (`concurrency.await`, `concurrency.join`, `concurrency.timeout`, and channels) and significantly improved the REPL with multi-line input, syntax highlighting, tab completion, persistent history, evaluation timing, and inline documentation.

<Note>
  The SCALF CLI binary is named `scalf`. Source files use the `.scl` extension. Pre-compiled bytecode cache files use the `.sclc` extension.
</Note>
